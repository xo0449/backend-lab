# 이벤트 SDK

[이벤트 수집 파이프라인](../event-collector)의 클라이언트 쪽이다.
두 모듈은 같은 파이프라인이지만 우선순위가 정반대다.

| | 무엇을 먼저 지키는가 |
|---|---|
| 수집기 | 데이터 정합성 |
| SDK | 호스트 앱을 멈추지 않는 것 |

## 고민

분석 코드 때문에 서비스가 멈추는 것은 어떤 경우에도 정당화되지 않는다.
이벤트를 하나도 못 받는 것보다 앱이 흰 화면이 되는 쪽이 훨씬 나쁘다.

그래서 이 SDK는 **정확성을 먼저 포기한다.** 실패하면 조용히 버리고,
큐가 넘치면 오래된 것을 버리고, 오류는 밖으로 내보내지 않는다.

## 공개 인터페이스

작게 유지한다. 넓은 인터페이스는 되돌리기 어렵다.

```typescript
export interface EventSdk {
  track(name: string, payload?: Record<string, unknown>): void
  flush(): Promise<void>
  flushSync(): void
}
```

`track`이 값을 반환하지 않고 기다리지도 않는 것이 핵심이다.
호출한 쪽은 이벤트가 갔는지 알 수 없고, 알 필요도 없다.
Promise를 반환하면 누군가는 `await`를 붙이고, 그 순간 분석 코드가
사용자 대기 시간에 들어간다.

## 만들면서 잡은 것

테스트를 돌리다 이런 경고가 나왔다.

```
Unhandled Rejection
Error: network down
 ❯ send modules/event-sdk/src/sdk.ts:71
 ❯ safely modules/event-sdk/src/sdk.ts:40
```

`safely()`로 감쌌는데도 오류가 새어 나갔다.
`try/catch`는 **동기** 예외만 잡는다. 전송이 비동기로 실패하면
`void send(...)`가 처리되지 않은 거부가 되어 밖으로 나간다.
Node는 기본 설정에서 이걸로 프로세스를 죽인다.

**분석 코드가 서비스를 내리는 정확한 경로였다.** 이 SDK가 막으려던
바로 그 일을 SDK 자신이 하고 있었다.

전송 함수 안에서 `try/catch`로 잡도록 고쳤다. 이제 `send`는
어떤 경우에도 거부하지 않는다. 회귀를 막는 테스트를 같이 넣었다.

```typescript
it('전송이 거부해도 처리되지 않은 거부가 생기지 않는다', async () => {
  const rejections: unknown[] = []
  process.on('unhandledRejection', (e) => rejections.push(e))
  ...
  expect(rejections).toHaveLength(0)
})
```

`expect(() => ...).not.toThrow()`만으로는 이걸 못 잡는다.
동기 예외만 확인하기 때문이다. 같은 실수를 되풀이하기 쉬운 지점이다.

## 결정과 이유

### 왜 실패해도 재시도하지 않는가

전송이 실패하는 상황은 대개 네트워크가 이미 나쁠 때다.
그때 재시도를 걸면 이미 느린 회선에 요청을 더 쌓는다.
사용자가 겪는 것은 "이벤트가 안 갔다"가 아니라 "앱이 느리다"가 된다.

분석 이벤트는 유실을 감당할 수 있는 데이터다. 결제나 정산이라면
답이 달라진다. 그 경우 애초에 이런 SDK로 보내면 안 된다.

### 왜 beforeunload가 아니라 visibilitychange인가

모바일 브라우저는 탭을 백그라운드로 보내거나 앱을 전환할 때
`beforeunload`를 부르지 않는 경우가 있다. 그대로 두면 모바일
사용자의 마지막 이벤트가 통째로 사라진다.

`visibilitychange`의 `hidden` 상태는 그 상황에서도 불린다.
전송은 `sendBeacon`을 쓴다. 페이지가 사라져도 브라우저가 끝까지 보낸다.

### 왜 환경 감지를 어댑터로 분리했는가

`typeof window !== 'undefined'` 같은 분기를 본체에 흩뿌리면
테스트가 어려워진다. 전송을 인터페이스로 빼두면 가짜를 끼워
넣을 수 있고, 새 환경이 생겨도 어댑터만 추가하면 된다.

서버 환경에서 `document`를 건드려 죽지 않는지 확인하는 테스트가 있다.
브라우저 전용 코드가 서버 렌더링에서 터지는 것은 흔한 사고다.

## 번들 크기

| | 크기 |
|---|---:|
| minify | 1,424 bytes |
| minify + gzip | 771 bytes |

```bash
npx esbuild modules/event-sdk/src/sdk.ts --bundle --minify --format=esm --outfile=/tmp/sdk.min.js
```

의존성이 없다. 이게 크기를 작게 유지하는 유일하고 확실한 방법이다.
SDK는 호스트 앱의 번들에 들어가므로 라이브러리를 하나 넣을 때마다
모든 사용자의 다운로드가 늘어난다.

## 다시 한다면

**버전 호환을 실제로 시험해봐야 한다.** 지금은 `schemaVersion`을 1로
고정해 보낸다. 옛 SDK를 쓰는 앱이 남아 있을 때 새 수집기가 어떻게
받을지는 [수집기 모듈의 스키마 실험](../event-collector)에서 절반만
다뤘다. SDK 쪽에서 버전을 올려보는 실험이 빠져 있다.

**샘플링이 없다.** 트래픽이 커지면 모든 이벤트를 보낼 이유가 없다.
다만 샘플링은 어떤 이벤트를 버려도 되는지 아는 상태에서 넣어야 한다.
지금 넣으면 근거 없는 숫자가 된다.

**큐를 버릴 때 아무도 모른다.** 상한을 넘겨 버린 건수를 세어
가끔 같이 보내면 "데이터가 왜 적지"를 추적할 수 있다.
지금은 조용히 사라진다.
