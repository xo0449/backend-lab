# 이벤트 수집 파이프라인

## 고민

이벤트 수집은 유실과 중복 사이의 타협이다. 둘 다 막으려면
보내는 쪽과 받는 쪽이 매번 확인을 주고받아야 하고, 그러면 느려진다.

**중복을 받아들이고 나중에 거르는 쪽을 골랐다.** 이벤트는 분석용이라
같은 것이 두 번 들어와도 나중에 지울 수 있지만, 안 들어온 것은
되살릴 수 없다. 그래서 받는 쪽은 최대한 관대하게, 거르는 일은
적재 시점으로 미룬다.

## 구조

| 실제 | 이 모듈 |
|---|---|
| 앱 API, 프론트 | 테스트 스크립트 |
| S3 | MinIO 컨테이너 |
| Redshift | DuckDB |

MinIO를 쓴 이유는 S3와 API가 같아서다. 엔드포인트만 바꾸면
코드 수정 없이 실제 S3로 간다.

```
클라이언트 → 수집기 → 버퍼 → 객체 저장소 → 적재 → 분석 저장소
```

## 결정과 이유

### 파일을 언제 끊을 것인가

크기 1,000건과 시간 10초 중 먼저 오는 쪽이다.

크기만 쓰면 트래픽이 적을 때 이벤트가 버퍼에 영원히 남는다.
새벽에 들어온 이벤트가 아침까지 안 나간다.
시간만 쓰면 몰릴 때 파일 하나가 감당 못 하게 커진다. 둘 다 필요하다.

### 파티션을 어느 시각으로 나눌 것인가

서버가 받은 시각이다. 클라이언트 시각은 함께 저장하되 쓰지 않는다.

기기 시계는 틀린다. 시간대가 어긋나기도 하고 사용자가 바꾸기도 한다.
2019년으로 설정된 기기에서 온 이벤트가 `dt=2019-03-04` 파티션에
들어가면 그 데이터는 사실상 사라진다. 아무도 그 날짜를 다시 읽지 않는다.

### 중복을 어디서 거를 것인가

적재 시점에 `eventId` 기준으로 거른다.

수집 단계에서 걸려면 무엇을 이미 받았는지 알아야 한다.
그 상태를 어딘가 두고 매 요청마다 조회하면 수집이 느려진다.
수집은 빨라야 한다. 이벤트를 보낸 쪽이 기다리고 있기 때문이다.

적재가 멱등하면 재시도를 마음 놓고 할 수 있다. 같은 파일을 두 번
넣어도 결과가 같다. 이게 파이프라인 전체를 단순하게 만든다.

### 왜 JSON 배열이 아니라 한 줄에 하나인가

파일이 중간에 끊겨도 앞부분은 읽을 수 있다. 이어붙이기도 쉽다.
JSON 배열은 닫는 괄호가 없으면 통째로 못 읽는다.

## 만들면서 고친 것

버퍼가 크기 조건으로 쓰기를 시작할 때 `flush()`가 그 쓰기를
기다리지 않았다. "flush를 기다렸는데 아직 안 써졌다"가 생겼다.
테스트가 이걸 잡았다.

진행 중인 쓰기를 집합으로 들고 있다가 `flush()`에서 함께 기다리도록
고쳤다. `push`는 여전히 동기다. 보내는 쪽을 기다리게 하지 않는다는
원칙은 유지했다.

## 스키마가 바뀌면 무엇이 깨지는가

`payload.itemId`를 `payload.items` 배열로 바꾼 상황을 만들어봤다.
v1 이벤트 2건과 v2 이벤트 3건을 한 테이블에 넣었다.

```bash
npx tsx modules/event-collector/bench/schema-change.ts
```

```
버전별 적재: [ [1, 2], [2, 3] ]
itemId를 읽는 쿼리: [ [5, 2] ]
두 버전을 함께 읽는 쿼리: [ [8] ]
```

**옛 형식만 아는 쿼리는 5건 중 2건만 센다. 그런데 오류가 나지 않는다.**
나머지 3건은 NULL이 되어 조용히 빠진다. 대시보드 숫자가 60퍼센트
줄어드는데 아무도 알림을 받지 않는다.

그래서 `schemaVersion`을 이벤트마다 저장한다. 버전별 건수를 세어보면
새 버전이 들어오기 시작한 시점을 알 수 있고, 쿼리를 고쳐야 한다는
신호가 된다.

## 다시 한다면

**버전별 건수에 알림을 건다.** 위 실험이 보여주듯 스키마 변경은
오류가 아니라 침묵으로 나타난다. 새 `schemaVersion`이 처음 등장할 때
알림이 오면 대시보드가 틀린 채로 몇 주 가는 일을 막을 수 있다.

**수집기가 죽으면 버퍼에 있던 이벤트는 사라진다.** 지금은 메모리에만
있다. 프로세스를 재시작할 때 손실을 감수한다는 뜻이다.
분석용 이벤트라 받아들일 만한 타협이지만, 이걸 결제나 정산에 쓰면
안 된다. 그 경우 버퍼를 디스크나 큐로 옮겨야 한다.

**파일이 너무 작게 쪼개진다.** 10초마다 끊으면 한산한 시간대에
작은 파일이 잔뜩 생긴다. 객체 저장소는 작은 파일이 많으면 읽기가
느려진다. 나중에 합치는 작업을 따로 두거나, 한산할 때는 간격을
늘리는 편이 낫다.
