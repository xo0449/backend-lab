# 다중 인스턴스에서 크론이 중복 실행되는 문제

## 고민

크론을 애플리케이션 프로세스 안에 등록하면 인스턴스 수만큼 돈다.
로컬에서는 하나라 문제가 없다가, 컨테이너를 늘리는 순간 드러난다.

이 배치는 조건에 맞는 아이템을 찾아 결과 테이블에 넣는다.
읽고, 계산하고, 쓴다. 읽기와 쓰기 사이에 틈이 있어서 두 실행이
같은 스냅샷을 보면 둘 다 "아직 없다"고 판단하고 같은 행을 넣는다.

단일 프로세스를 가정한 코드가 어디서 깨지는지 보여주는 사례다.

## 재현

워커 4개를 동시에 돌린다.

```bash
npm run db:up
npx tsx modules/cron-duplicate-execution/bench/seed.ts
npx tsx modules/cron-duplicate-execution/bench/run.ts
```

```json
{
  "mode": "naive",
  "workers": 4,
  "insertedPerWorker": [1500, 1500, 1500, 1500],
  "totalRows": 6000,
  "distinctItems": 1500,
  "duplicated": 4500
}
```

네 워커가 각각 1500건을 넣었다. 실제로 필요한 건 1500건이다.

## 접근

MySQL 네임드 락으로 인스턴스 간 하나만 실행되게 직렬화했다.

```bash
MODE=lock npx tsx modules/cron-duplicate-execution/bench/run.ts
```

```json
{
  "mode": "lock",
  "workers": 4,
  "insertedPerWorker": [1500, 0, 0, 0],
  "totalRows": 1500,
  "duplicated": 0
}
```

### 왜 유니크 제약이 아닌가

`(condition_id, item_id)`에 유니크 제약을 걸면 중복 행은 막힌다.
하지만 배치가 네 번 도는 것 자체는 그대로다. 나머지 세 번은
전부 실패하고, 그 실패를 무시할지 재시도할지 또 정해야 한다.
증상을 막는 것과 원인을 없애는 것은 다르다.

제약은 여전히 넣는 게 맞다. 마지막 방어선으로는 유효하다.
다만 그것만으로는 부족하다는 게 이 실험의 결론이다.

### 왜 Redis 분산 락이 아닌가

의존성이 하나 늘어난다. 이미 MySQL을 쓰고 있고, 배치는 어차피
그 MySQL에 쓴다. 락과 데이터가 같은 곳에 있으면 생각할 것이 줄어든다.

Redis가 필요해지는 경우는 있다. 락을 잡는 쪽과 데이터를 쓰는 쪽이
다른 저장소일 때, 또는 락 획득 빈도가 높아 DB 커넥션을 오래
점유하는 것이 부담일 때다. 자정에 한 번 도는 배치는 둘 다 아니다.

### 왜 즉시 반환인가

`GET_LOCK(name, 0)`은 락을 못 잡으면 바로 0을 준다.
대기하게 만들면 첫 번째가 끝난 뒤 두 번째가 깨어나 같은 일을
다시 한다. 이미 처리된 상태라 삽입할 것이 없긴 하지만,
전체 스캔을 네 번 하게 된다. 배치에서는 건너뛰는 편이 맞다.

### 왜 같은 커넥션이어야 하는가

네임드 락은 커넥션 단위다. 풀에서 커넥션을 매번 새로 꺼내면
`RELEASE_LOCK`이 락을 잡지 않은 커넥션에서 실행되어 0을 반환하고,
락은 그대로 남는다.

그래서 `getConnection()`으로 하나를 잡고 획득부터 해제까지 유지한다.
해제는 `finally`에 둔다. 예외가 나도 락이 남지 않아야 한다.

## 결과

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 중복 행 | 4,500 | 0 |
| 총 행 수 | 6,000 | 1,500 |
| 실제 삽입한 워커 | 4 | 1 |

## 다시 한다면

**스케줄러를 애플리케이션에서 분리한다.** 락은 증상을 막는 해결이다.
크론이 프로세스마다 등록된다는 구조 자체가 원인이다. 별도 스케줄러가
작업을 큐에 넣고 워커가 꺼내 가면 중복 실행이 애초에 생기지 않는다.

다만 그건 인프라가 하나 늘어나는 일이다. 배치가 몇 개 안 될 때는
락 한 줄이 합리적인 타협이다. 배치가 늘어나면 그때 옮긴다.

**락을 잡은 인스턴스가 죽으면 어떻게 되는가.** 커넥션이 끊기면
MySQL이 락을 자동으로 푼다. 그래서 영구 교착은 없다.
대신 그 회차는 중간까지만 처리된 채 끝난다. 배치가 중간부터
다시 시작할 수 있는 구조인지는 별개로 확인해야 한다.
이 실험에서는 다루지 않았다.
